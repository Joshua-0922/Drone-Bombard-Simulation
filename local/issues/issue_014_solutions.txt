================================================================================
 방안 A: CCIP 기반 가상 drop (물리 drop 포기)
================================================================================

  개요:
    실제 payload 낙하 시뮬레이션을 포기하고, CCIP 운동학 예측값을
    drop_error로 사용. DetachableJoint 완전 불필요.

  구현:
    - drone_drop_env.py의 drop 시 publish_drop() 호출 제거
    - drop_calculator 대신 CCIP _predict_impact_point()의 d_impact을
      직접 drop_error로 사용
    - drop_error = d_impact (CCIP 예측 착탄 오차)
    - 코드 변경 ~20줄

  장점:
    - 구현 가장 간단
    - DetachableJoint 문제 완전 우회
    - infra restart 불필요 (drop 후 joint 복원 필요 없음) → Issue #011 해결
    - 학습 속도 대폭 향상 (drop 시 30초 restart → 0초)

  단점:
    - CCIP 예측 ≠ 실제 물리 → Issue #007 (CCIP 갭) 문제 해결 불가
    - 에이전트가 학습하는 건 "CCIP 최적화"이지 "실제 정밀 투하"가 아님
    - 나중에 실제 drop으로 전환 시 성능 차이 발생 가능
    - prediction_bonus (#010) 의미 없어짐 (gap 항상 0)

  기대:
    - 학습 속도 5~10배 향상
    - CCIP 기준으로 drop_error 감소 가능성 높음
    - 하지만 실제 투하 정확도는 별도 검증 필요

================================================================================
 방안 C: 이중 모델 (payload 드론 + PX4 드론 분리)
================================================================================

  개요:
    pre-spawn 드론(DetachableJoint 포함, PX4 미연결)과
    PX4 제어 드론(DetachableJoint 없음)을 동일 위치에 배치.
    PX4 드론의 움직임을 pre-spawn 드론에 동기화.

  구현:
    - world SDF: x500_bombard (payload 포함) pre-spawn
    - PX4: 별도 x500 (payload 없음) spawn
    - 매 step PX4 드론의 pose를 읽어 pre-spawn 드론에 set_pose
    - drop 시 pre-spawn 드론의 DetachableJoint에 명령

  장점:
    - 실제 물리 drop 사용 가능
    - PX4 소스 수정 불필요

  단점:
    - 동일 위치에 2개 모델 → 물리 충돌 위험
    - pose 동기화 지연 → payload 위치 부정확
    - 구현 복잡도 높음
    - 성능 오버헤드 (2배 모델)

  기대:
    - 작동 가능하지만 안정성 우려
    - 물리 충돌 해결이 핵심 과제


================================================================================
 방안 D: Gazebo 서비스로 런타임 joint 생성
================================================================================

  개요:
    PX4가 드론을 spawn한 후, Gazebo 서비스 API로
    DetachableJoint를 런타임에 생성.

  구현:
    - PX4 spawn 완료 대기
    - gz service /world/.../entity_system/add 로 DetachableJoint 플러그인 추가
    - 또는 gz service로 fixed joint를 직접 생성

  장점:
    - PX4 기존 방식 유지 (PX4_SIM_MODEL spawn)
    - SDF 수정 최소화

  단점:
    - Gazebo Harmonic에서 런타임 플러그인/joint 추가 API 지원 여부 불확실
    - API가 있더라도 DetachableJoint의 detach 기능까지 지원하는지 불확실
    - 실험적 접근

  기대:
    - API가 지원되면 깔끔한 해결
    - 지원 안 되면 불가능

 방안 E: drop_calculator 수정 (payload 추적 대신 CCIP + 물리 보정)
================================================================================

  개요:
    방안 A의 변형. CCIP 예측에 물리 보정 항을 추가하여
    실제 drop에 가까운 결과를 계산.

  구현:
    - drop_error = d_impact + correction(speed, altitude, wind)
    - correction은 이전 학습 데이터에서 추출하거나 물리 모델로 계산
    - 또는 공기저항 항 추가: t_f에 drag coefficient 반영

  장점:
    - DetachableJoint 불필요
    - 방안 A보다 물리적으로 정확
    - infra restart 불필요

  단점:
    - 보정 모델의 정확도가 핵심 — 잘못되면 방안 A와 차이 없음
    - 보정 파라미터 튜닝 필요
    - 실제 물리와 여전히 차이 존재

  기대:
    - CCIP 단독보다 정확
    - 하지만 실제 물리 시뮬레이션에는 미치지 못함

================================================================================
 방안 B 조사 진행 — PX4 gz_bridge 소스 분석
================================================================================

파일: /opt/PX4-Autopilot/src/modules/simulation/gz_bridge/GZBridge.cpp

PX4_SIM_MODEL 경로 (-m 옵션):
  model_sim = "gz_x500_bombard"
  → init()에서 EntityFactory service call로 모델 spawn
  → req.set_name(_model_name) — 모델 이름 덮어씀
  → req.set_sdf_filename(model_sim + "/model.sdf")

PX4_GZ_MODEL_NAME 경로 (-n 옵션):
  model_sim = "" (비어있음)
  → init()에서 _model_sim.empty() == true → spawn 안 함
  → 기존 모델의 토픽에 구독만 연결

PX4_GZ_MODEL_NAME만 사용하면 spawn 없이 토픽 구독만 하는데도
DetachableJoint가 깨지는 이유 미확인.
추정: PX4가 센서 토픽(IMU, barometer 등)을 구독하면서
Gazebo ECM에 변경을 가하는 것이 joint에 영향.

추가 조사 필요:
  - Gazebo ECM에서 PX4 토픽 구독 시 어떤 컴포넌트가 변경되는지
  - DetachableJoint의 PreUpdate에서 joint 생성 조건 소스 확인
  - gz-sim8 DetachableJoint 소스코드 (GitHub에서 확인)
