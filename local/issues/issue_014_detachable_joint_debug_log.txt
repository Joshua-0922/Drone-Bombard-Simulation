--- 2-16. drop_error 변동 문제 ---

사용자 지적: "payload가 항상 같은 위치면 drop_error도 항상 같아야 하는데,
실제로는 14.26~15.09m로 변동한다. 뭔가 움직이고 있다는 뜻."

관찰:
  payload가 바닥에서 미세하게 drift (물리 settling)
  spawn 시 z=0.14 → 바닥 z=0으로 떨어지면서 x,y 방향으로 소폭 이동
  (0, 0, 0.14) → (0.9, 0.5, 0.0) 또는 (1.2, 1.4, 0.0)
  이 drift가 drop_error 변동의 원인

  예외 outlier (20.39m): 큰 drift 또는 다른 에피소드 상태

  - inline 정의로 변경하면 해결되는지 테스트 필요

--- 2-17. 최소 테스트로 merge include 원인 확인 ---

테스트 A: inline 모델 (parent_box + child_ball + DetachableJoint)
  parent_box: inline 정의, static=true, z=1.0
  child_ball: inline 정의, z=0.9

  결과:
    BEFORE drop: child z = 0.900000 (parent에 붙어있음!)
    AFTER drop:  child z = 0.050000 (바닥으로 떨어짐!)
    → DetachableJoint 정상 작동

테스트 B: parent를 <include merge="true">로 변경 (나머지 동일)
  parent_box:
    <include merge="true">
      <uri>/tmp/test_parent_model</uri>
    </include>
    + DetachableJoint 플러그인

  결과:
    BEFORE drop: child z = 0.050000 (처음부터 바닥!)
    AFTER drop:  child z = 0.050000 (변화 없음)
    → joint가 형성되지 않음. child가 처음부터 바닥에 떨어짐.

결론:
  <include merge="true">가 DetachableJoint를 깨뜨림.
  merge include로 parent 모델을 포함하면 DetachableJoint가
  parent_link를 찾지 못해 joint가 형성되지 않음.

  이것이 프로젝트 시작부터 payload가 드론에 안 붙었던 근본 원인.
  x500_bombard가 <include merge="true"><uri>model://x500</uri></include>
  사용 → DetachableJoint 무력화.


================================================================================
 4. 근본 원인
================================================================================

Gazebo Harmonic(gz-sim8)의 DetachableJoint 플러그인은
<include merge="true">로 포함된 모델의 link를 parent_link로 사용할 수 없음.

Configure 단계에서 토픽 등록은 성공하지만,
PreUpdate에서 GetChildModelAndLinkEntities()가 parent_link를
찾지 못해 joint 생성이 silent fail.

해결: merge include 제거, x500 + x500_base 내용을 inline으로 합침.


================================================================================
 5. 해결
================================================================================

  x500_bombard/model.sdf에서:
    변경 전: <include merge="true"><uri>model://x500</uri></include>
             (x500도 <include merge="true"><uri>model://x500_base</uri></include>)
    변경 후: x500_base + x500의 모든 내용을 inline으로 직접 포함

  영향 파일: x500_bombard/model.sdf (원본)
  r0~r3 변형은 이후 동일 패턴 적용.

--- 7-1. PX4 없이 Gazebo만 → payload 부착 확인 ---

--- 7-2. PX4_GZ_MODEL_NAME으로 연결 시 → joint 파괴 ---

drone_drop_env.py 수정:
  PX4_SIM_MODEL 제거 → PX4_GZ_MODEL_NAME=x500_bombard_0
  world SDF에 drone inject (pre-spawn)
  Gazebo -r (즉시 실행)

결과:
  drone: (0.02, 0.05, 4.71) — PX4 연결 + takeoff 성공
  payload: z=0.0 — 바닥. joint 파괴됨.


--- 7-3. Gazebo paused 시작 + PX4 연결 후 unpause → 실패 ---

Gazebo를 -r 없이 paused로 시작
PX4 연결 후 5초 대기
gz service로 unpause

결과:
  payload: z=0.0 — 여전히 바닥.


--- 7-4. 현재 확인된 사실 ---

  - Gazebo만 (PX4 없이): inline SDF + pre-spawn → joint 정상 ✓
  - PX4_GZ_MODEL_NAME으로 연결: joint 파괴 ✗
  - PX4_SIM_MODEL로 spawn: joint 형성 안 됨 (타이밍) ✗
  - infra.launch.py + PX4_SIM_MODEL: pre-spawn + 두 번째 드론 spawn
    → pre-spawn 드론의 joint 작동, PX4는 두 번째 드론 제어

  PX4가 모델에 연결/spawn할 때 Gazebo ECM에 변경을 가해
  DetachableJoint가 무력화되는 것으로 추정.
