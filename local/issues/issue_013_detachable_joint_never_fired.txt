================================================================================
 1. 문제점
================================================================================

  Gazebo의 DetachableJoint 플러그인이 drop 명령을 수신해도
  payload를 물리적으로 분리하지 않았다.

  학습 코드(drone_drop_env.py)는 drop이 발생했다고 기록하고 보상을 계산했지만,
  실제 Gazebo 시뮬레이션에서는 payload가 드론에 붙어 있는 채로
  에피소드가 끝까지 진행되었다.

  이로 인해:
    - drop_error(착탄 오차)가 payload의 낙하 위치가 아니라
      드론이 최종적으로 바닥에 닿은 위치(crash/착륙)와 타겟의 거리로 측정됨
    - 에이전트는 "정밀 투하"가 아니라 "타겟 근처에서 crash하기"를 학습
    - 프로젝트 시작부터 현재까지 모든 학습의 drop_error 데이터가 무효

 3. 원인 분석
================================================================================

  3-1. 직접 원인: SDF 태그 오류

    우리 model.sdf:
      <plugin name="gz::sim::systems::DetachableJoint"
              filename="gz-sim-detachable-joint-system">
        <parent_link>payload_mount</parent_link>
        <child_model>payload_0</child_model>
        <child_link>payload_link</child_link>
        <topic>/x500_0/drop</topic>             ← 잘못된 태그
      </plugin>

    Gazebo Harmonic(gz-sim8) 공식 예제:
      <plugin name="gz::sim::systems::DetachableJoint" ...>
        <parent_link>chassis</parent_link>
        <child_model>B1</child_model>
        <child_link>body</child_link>
        <detach_topic>/B1/detach</detach_topic>  ← 올바른 태그
      </plugin>

    gz-sim8의 DetachableJoint 플러그인은 <detach_topic> 태그를 사용한다.
    <topic> 태그는 인식되지 않아 무시되며, 플러그인의 기본 동작도
    detach 명령을 수신하지 않는 상태가 된다.

    참고: /usr/share/gz/gz-sim8/worlds/detachable_joint.sdf (공식 예제)

  3-2. 왜 발견이 늦었는가

    drop_calculator 노드가 "drop이 발생했다"고 잘못 판정했기 때문이다.
    데이터 파이프라인을 따라가면:

      drone_drop_env.py → publish_drop() 호출
        ├─ /payload/drop_cmd (Empty)      → bridge → /x500_0/drop (Gazebo)
        │                                            → DetachableJoint 무시 ✗
        └─ /drone/payload/drop_cmd_raw (Bool False) → drop_calculator 수신 ✓

    drop_calculator는 Bool(False)를 수신하면 is_falling=True로 설정하고
    payload 위치(/drone/payload/position)를 추적하기 시작한다.
    payload가 실제로 분리되지 않았으므로, payload 위치 = 드론 위치.
    드론이 crash하거나 착륙하여 z ≤ 0.04m이 되면 "착탄"으로 판정한다.

    즉, drop_error는:
      의도: payload가 낙하하여 지면에 닿은 위치와 타겟의 거리
      실제: 드론이 바닥에 닿은 위치와 타겟의 거리

    두 경로가 분리되어 있어서, 한쪽(ROS2)은 정상 동작하고
    다른 쪽(Gazebo 물리)은 실패했지만, 학습 코드는 정상으로 인식했다.

 4. 영향 범위
================================================================================

  4-1. 영향받은 학습 (전부)

    junsang_v2 (200k)     — critic 발산으로 실패, drop_error도 가짜
    junsang_v3 (200k)     — 정책 학습 실패, drop_error도 가짜
    junsang_v4 Tier 1     — drop 220회 기록, 전부 가짜 (드론 crash 위치)
    junsang_v4 150k 재학습 — drop 275회 기록, 전부 가짜
    Round 1 (dv428atu)    — drop 259회 기록, 전부 가짜

    모든 학습에서:
    - drop_error_actual_m: 실제 payload 낙하 오차가 아님
    - total_success_count: 드론 crash 위치 기준 (의미 없음)
    - total_jackpot_count: 마찬가지
    - prediction_gap(d_impact - d_error): d_error가 가짜이므로 무의미

  4-2. 영향받은 결정

    이전 학습 결과에 기반한 모든 분석과 결정이 잘못된 데이터에 기반함:
    - "drop_error가 12~14m에 수렴" → 드론 crash 위치가 12~14m이었을 뿐
    - "정밀도가 개선되지 않음" → 정밀도를 측정한 적이 없었음
    - Issue #001 (보상 정밀도), #003 (스케일), #007 (CCIP 갭):
      진단 자체는 유효하나, 수치 근거는 재검증 필요
    - Issue #009 (졸업 기준): 기준이 되는 수치가 전부 무효

  4-3. 영향받지 않은 부분

    - Layer 2, 3 (per-step 보상): 드론 비행 자체와 관련, payload 무관
    - SAC 하이퍼파라미터 결정 (gradient_steps, gamma): 학습 안정성 관련
    - 종료 조건 (crash, overspeed, inverted 등): payload 무관
    - 인프라 안정성 패치 (jekyun_v2): 여전히 유효
    - Hybrid drop 메커니즘 설계: 설계 자체는 유효, 학습 결과만 무효
    - 보상 함수 재설계 방향: "정밀도에 민감하게" 원칙은 유효

 5. 해결
================================================================================

  5-1. SDF 수정 (완료)

    8개 model.sdf 파일에서:
      변경 전: <topic>/x500_N/drop</topic>
      변경 후: <detach_topic>/x500_N/drop</detach_topic>

  5-2. 수정 검증 (완료)

    수정 후 Gazebo 재시작, 수동으로 gz topic 명령 전송:
      gz topic -t /x500_0/drop -m gz.msgs.Empty -p 'unused: true'
    → GUI에서 payload가 물리적으로 분리되어 낙하하는 것 확인 ✓

  5-3. 재학습 필요

    모든 이전 학습 결과가 잘못된 보상 신호에 기반하므로,
    SDF 수정 후 fresh start로 재학습해야 한다.

    재학습 전 확인 사항:
      - 5k dry-run에서 payload가 실제로 낙하하는지 GUI 확인
      - drop_calculator가 실제 payload 착탄 위치를 정확히 측정하는지 확인
      - drop_error가 이전과 다른 패턴을 보이는지 확인
        (이전: 12~14m 수렴 = 드론 crash 위치)
        (수정 후: 실제 payload 낙하 궤적에 의한 오차)

 6. 교훈 및 재발 방지
================================================================================

  6-1. 이 버그가 오래 살아남은 구조적 원인

    - drop 명령의 경로가 ROS2(drop_calculator)와 Gazebo(DetachableJoint)로
      분리되어 있었음
    - ROS2 쪽은 정상 동작하여 학습 코드가 "drop 성공"으로 인식
    - Gazebo 쪽은 실패했지만 학습 코드에서 물리적 분리를 직접 확인하지 않음
    - drop_calculator가 payload 위치를 추적하지만, payload가 드론에 붙어 있으면
      드론 위치 = payload 위치이므로 "정상적으로 낙하 중"으로 오해

  6-2. 재발 방지 체크리스트

    □ 학습 시작 전 GUI로 1 에피소드 확인: payload 물리 분리 눈으로 확인
    □ SDF 변경 시 Gazebo 공식 문서/예제와 태그명 대조
    □ drop_calculator에 "payload가 드론에서 실제로 분리되었는가" 검증 로직 추가 고려
      (예: payload 위치와 드론 위치의 거리가 일정 이상 벌어지는지 확인)
    □ 새 환경/모델 도입 시 end-to-end 물리 검증 (명령 → 물리 반응 → 측정) 필수
