────────────────────────────────────────────────────────────────────────────────
 표기 약속 (이 가이드 전체에 적용)
────────────────────────────────────────────────────────────────────────────────

  [host]    호스트 셸 (보통의 SSH/터미널) 에서 실행
  [ctr]     docker exec ... 로 컨테이너 안에서 실행
  [tmux]    tmux 세션 안의 어느 페인에서 실행

  파일 경로:
    /home/juns/...                  →  호스트 경로
    /workspace/...                  →  컨테이너 안 경로
    /tmp/train.log                  →  컨테이너 안 /tmp  (호스트 /tmp 아님)

  Ctrl 키 표기:
    Ctrl+B → D       Ctrl 누른 채 B 치고, 둘 다 떼고, D 따로 치기
                     (tmux prefix 기본값 = Ctrl+B)


################################################################################
#  STEP 0 — 회의 결정 사항 정리 (시작 전 1분)
################################################################################

회의 결정값을 여기에 받아 적은 다음 STEP 1 로 진행:

[ ] M3  total_timesteps     :  __________     (200k / 500k / 1M / 2M / 기타)
[ ] L7  PX4 영구화           :  __________     (A 지금 / B Dockerfile / C 나중)
[ ] N1  Drop Sparse Signal   :  __________     (A curriculum / B w_impact↑ / C 분할 / D 그대로)

위 3개 결정 외 H1/H2/H3/M1/M2/L4/L6 는 이미 적용·검증 완료. 추가 작업 없음.

⚠ N1=A 또는 C 를 선택했다면 별도 코드 패치가 필요합니다.
   가이드 한 줄로 안 끼워지는 작업 (env 의 누적 step 추적 구조 추가 등).
   회의 후 별도로 코드 작업 후 본 학습 진입하세요. STEP 2-2 참조.

 1-2. PX4 airframe rootfs 점검 (양쪽 분기)
────────────────────────────────────────────────────────────────────────────────

[host]

  분기:
    [A] 4016~4019 가 모두 보임   →  airframe OK.  그대로 STEP 2 로.
    [B] 출력이 비거나 일부만 보임 →  컨테이너 재생성/리빌드로 다 사라졌거나 부분 누락.
                                    아래 L7 결정에 따라 처리:

  [B-1]  L7 = A (지금 영구화)

    docker exec drone-bombard-harmonic bash -c \
      'cd /opt/PX4-Autopilot && make px4_sitl_default'
    # 15~20분 소요.  끝난 후 위 ls 명령 다시 쳐서 4016~4019 다 보이는지 확인.

  [B-2]  L7 = B 또는 C (영구화 안 함 / 나중에)

    docker exec drone-bombard-harmonic bash -c '
    SRC=/opt/PX4-Autopilot/ROMFS/px4fmu_common/init.d-posix/airframes
    DST=/opt/PX4-Autopilot/build/px4_sitl_default/rootfs/etc/init.d-posix/airframes
    for f in 4016_gz_x500_bombard_r0 4017_gz_x500_bombard_r1 \
             4018_gz_x500_bombard_r2 4019_gz_x500_bombard_r3; do
      cp -v "$SRC/$f" "$DST/$f"
    done'
    # 즉시 끝남.  컨테이너 라이프타임 동안 유효.

────────────────────────────────────────────────────────────────────────────────
 2-1. hyperparams.yaml — M3 (total_timesteps) 갱신
────────────────────────────────────────────────────────────────────────────────

[host]  편집기로 열기 (nano 가 가장 단순):

    nano /home/juns/Drone-Bombard-Simulation/ros2_ws/src/rl_navigation/config/hyperparams.yaml

  vim 선호 시:  vim /home/juns/Drone-Bombard-Simulation/ros2_ws/src/rl_navigation/config/hyperparams.yaml
  GUI 편집기 (VSCode 등) 있으면 그것도 OK.

  바꿀 곳 — training 섹션:

    training:
      total_timesteps: <STEP 0 의 M3 값>      ← 이 한 줄만 필수 변경

  같은 섹션의 eval_freq 도 본 학습이면 더 큰 값으로 권장 (선택사항):

      eval_freq: 2000  →  10000     # smoke 용 2000 → 본학습 10000 권장 (선택)

  저장 후 종료 (nano: Ctrl+O → Enter → Ctrl+X / vim: :wq).

────────────────────────────────────────────────────────────────────────────────
 2-2. N1 결정에 따라 추가 변경
────────────────────────────────────────────────────────────────────────────────

  N1 = D 권장 (그대로) →  추가 변경 없음.  2-3 으로.

  N1 = B (w_impact 강화) →
    같은 hyperparams.yaml 의 reward 섹션:

      w_impact: 2.0  →  5.0
      k_impact: 0.05 →  0.1

  N1 = A (curriculum threshold) 또는 N1 = C (terminal reward 시간 분할) →
    ⚠ 가이드 한 줄로 끼워지지 않는 코드 작업입니다.
    A: 환경 내부에 학습 시작부터의 누적 step 추적 구조 + threshold 동적 변경 로직 추가
    C: terminal reward 를 마지막 N step 에 progressive 하게 분배하는 새 로직
    회의 후 별도 패치로 진행하고, 그 코드 변경이 commit/적용된 다음 이 가이드 STEP 2-3 으로.

#  STEP 3 — WandB Incremental Sync 가동 (1분)

 4-2. 학습 시작 (왼쪽 페인)
────────────────────────────────────────────────────────────────────────────────

[tmux]  왼쪽 페인으로 이동

    Ctrl+B  →  ←

[tmux 왼쪽 페인]  컨테이너 안으로 진입 + 환경 source + 학습 시작

    docker exec -it drone-bombard-harmonic bash
    # 이제 컨테이너 셸 안 (프롬프트가 root@... 로 바뀜)

    source /opt/ros/humble/setup.bash
    source /workspace/ros2_ws/install/setup.bash
    cd /workspace/ros2_ws
    export WANDB_MODE=offline      # ⚠ 학습 재시작마다 매번 export 필요 (셸 변수)
    ros2 run rl_navigation train_sac 2>&1 | tee /tmp/train.log

  ⚠ 위 /tmp/train.log 는 컨테이너 안의 /tmp.  호스트의 /tmp 가 아님.
  ⚠ WANDB_MODE 가 그 셸 세션에만 유효.  학습 중단 후 재시작할 때 까먹지 말 것.

────────────────────────────────────────────────────────────────────────────────
 6-2. WandB 마지막 sync
────────────────────────────────────────────────────────────────────────────────

[host]  Incremental sync 가 다음 사이클까지 기다리지 않게 즉시 한 번 더
        ⚠ 주의: glob 으로 모든 옛 offline-run 까지 sync 시도하면, entity 가 바뀐

################################################################################
#  APPENDIX B — 중단된 학습 처리 (Ctrl+C / kill / 멈춤)
################################################################################

먼저 알아둘 점:

  • Ctrl+C (SIGINT) → train_sac 코드는 SIGINT 핸들러를 따로 두지 않음.
    프로세스가 즉시 죽고 sac_drop_preempt.zip 도 만들어지지 않음.
    → 이어서 재개하고 싶다면 가장 가까운 checkpoint (sac_drop_<N>_steps.zip) 에서 시작.

  • kill -TERM <pid> (SIGTERM) → _emergency_save 핸들러 발동.
    sac_drop_preempt.zip + sac_drop_preempt_replay.pkl 저장됨.
    → 가장 정확한 재개 (replay buffer 까지 포함).

  • WandB IPC 데드락으로 멈춤 → 프로세스 살아있지만 일은 안 함.
    pkill -KILL 로 죽이면 preempt 안 만들어짐.
    → 그래도 마지막 checkpoint 에서 재개 가능.

 B-3.  사용 가능한 재개 지점 확인
────────────────────────────────────────────────────────────────────────────────

[host]

  나오는 후보 :

    sac_drop_preempt_replay.pkl     ← preempt 와 짝
    sac_drop_<N>_steps.zip          ← checkpoint_freq 마다 자동 저장 (5000 step 마다)

    3) best_model.zip                 (성능 기준, 학습 진행도 아님)
