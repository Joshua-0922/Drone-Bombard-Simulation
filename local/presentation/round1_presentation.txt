 Drone-Bombard-Simulation — 강화학습 기반 드론 정밀투하
 발표 자료 (2026-05-25)

================================================================================
 1. 프로젝트 개요
================================================================================

  목표
    ROS2 + Gazebo + PX4 시뮬레이션 환경에서
    SAC(Soft Actor-Critic) 강화학습을 활용하여
    드론이 목표 지점에 정밀 투하하는 비행 정책을 학습한다.

  시뮬레이션 환경
    시뮬레이터    Gazebo Harmonic (Docker 컨테이너 내부)
    비행제어      PX4 SITL (Software-In-The-Loop)
    RL 프레임워크  Stable-Baselines3 SAC
    타겟          고정 좌표 (11m, 10m) ENU

  에이전트 설계
    관측 (17차원)  위치, 속도, 각속도, 타겟 상대좌표, CCIP 예측 낙하점, 탄착 예상시간 등
    행동 (5차원)   전후(vx), 좌우(vy), 상하(vz), 회전(yaw rate), 투하 결정(drop)

  학습 규모
    150k~200k step (약 1,000~1,500 에피소드)
    에피소드 1회 = 최대 500 step (약 25초, 20Hz 기준)


================================================================================
 2. 어떤 문제들을 겪었는가
================================================================================

  총 7회의 학습을 거치며 세 가지 유형의 실패를 경험했다.

  ─── 유형 1: 시뮬레이션 인프라 결함 ────────────────────────────────

    현상:
      CCIP(착탄점 예측)가 1m이라 했는데 실제 착탄 거리는 14.87m.
      모든 drop에서 약 14m의 체계적 오차가 반복됐다.

    원인:
      RL 알고리즘이 아닌 시뮬레이션 인프라의 버그였다.
      spin thread가 crash하면서 ROS2 콜백이 멈추고,
      CCIP 데이터가 갱신되지 않은 채 사용되었다.

    해결:
      인프라 안정성 패치가 적용된 jekyun_v2 브랜치로 전환.
      (resilient spin thread, reset 재귀 방지, 단계적 CRUISE 복구,
       프로세스 종료 강화 등 4종)
      → 전환 후 14m 오차 완전 해소 확인.

  ─── 유형 2: Critic 발산 ──────────────────────────────────────────

    현상:
      critic loss가 정상 범위(~100)에서 17,000까지 폭주.
      정책이 완전히 붕괴되어 학습 무의미.

    원인:
      gradient_steps=4로 설정하면 한 step의 경험으로 네트워크를 4번 갱신한다.
      이때 매 step의 작은 보상(±0.5)과 drop 시점의 큰 보상(최대 +350)이
      혼재된 데이터를 4배 빠르게 학습하면서 Q값 추정이 발산했다.

    해결:
      gradient_steps를 4에서 1로 되돌림.
      → critic 안정성 회복 확인.

  ─── 유형 3: 정밀도가 개선되지 않는 문제 (핵심) ────────────────────

    현상:
      드론이 투하 자체는 하지만(112k step 동안 220회),
      착탄 오차가 전혀 줄지 않았다.

      drop_error    평균 13.15m, 중앙값 12.89m → 수렴 정체
      성공 횟수     0회 (0.5m 이내 도달한 적 없음)
      뒤집힘(inverted)  전체 종료의 44% → 가장 흔한 실패 원인

    근본 원인 (4가지):
      ① 보상이 정밀도에 둔감 — 15m에서 drop하나 5m에서 drop하나 보상 차이가 작음
      ② 보상 스케일이 너무 큼 — 터미널 보상이 접근 신호를 덮어버려 타겟 방향 학습 실패
      ③ auto-drop 강제 발동 — 에이전트가 투하 타이밍을 스스로 결정할 수 없음
      ④ 종료 조건 부족 — 바운스나 역주행 에피소드가 500 step까지 끌려 학습 낭비

    이 네 가지가 Round 1 변경의 출발점이다. 아래 섹션에서 각각의 해결 방안을 설명한다.

 3. 보상 함수 재설계
================================================================================

  보상은 4개 Layer로 구성되어 있다.
  Layer 1~3은 매 step마다 부여되고, Layer 4는 투하 시점에 한 번 부여된다.

  이번 Round 1에서 가장 크게 바뀐 것은 Layer 4(투하 보상)이고,
  Layer 1(안전 페널티)의 스케일도 함께 조정했다.
  Layer 2(안정)와 Layer 3(접근)은 변경 없이 유지했다.

  ─── Layer 4: 투하 보상 (핵심 변경) ────────────────────────────────

    [ 이전 설계 ]

      R4 = 150                           bonus (정액, drop만 하면 지급)
         + 100 * exp(-0.3 * d_error)      정밀도
         + 100 * [d_error ≤ 0.1m]         jackpot

      이것이 왜 문제였는가:

      bonus가 150으로 고정되어 있어서, 멀리서 대충 drop해도 150을 받는다.
      정밀도 항의 decay(k2=0.3)도 완만해서, 15m drop과 5m drop의
      보상 차이가 겨우 21이다. 이미 150을 확보한 에이전트 입장에서
      21을 더 얻으려고 위험을 감수할 이유가 없다.

      거리별 보상 (이전):
        d_error  0m = 350 (jackpot 포함)
        d_error  5m = 172
        d_error 15m = 151  ← 학습이 수렴한 지점. 0m과 겨우 2.3배 차이.
        d_error 50m = 150  ← bonus만으로도 충분

    [ 현재 설계 — Round 1 ]

      R4 = 30 * exp(-0.3 * d_xy)                proximity bonus
         + 100 * exp(-0.5 * d_error)             정밀도
         + 20 * exp(-0.1 * |d_impact - d_error|) 예측 정확도 bonus
         + 50 * [d_error ≤ 0.1m]                 jackpot

    세 가지를 바꿨다.

    (1) 투하 bonus를 거리 의존형으로 교체

        이전: drop만 하면 무조건 150
        현재: 타겟에 가까이 가야 bonus를 받을 수 있다
              30 * exp(-0.3 * d_xy)

        d_xy = 50m (멀리서 즉시 drop)  →  bonus ≈ 0  (사실상 무보상)
        d_xy = 14m (이전 수렴 지점)    →  bonus = 0.5
        d_xy =  5m                     →  bonus = 6.7
        d_xy =  3m                     →  bonus = 12.2
        d_xy =  0m (타겟 바로 위)      →  bonus = 30

        → 에이전트에게 "가까이 가야 의미가 있다"는 신호를 준다.

    (2) 정밀도 decay 강화: k2를 0.3에서 0.5로

        decay가 가파르면 거리에 따른 보상 차이가 뚜렷해진다.

        d_error  5m:  이전 22  →  현재  8.2  (차이 3배)
        d_error 10m:  이전  5  →  현재  0.7  (차이 7배)
        d_error 15m:  이전  1  →  현재  0.06 (차이 17배)

        → "5m와 15m는 완전히 다른 결과"라는 것을 에이전트가 느낄 수 있다.

    (3) 예측 정확도 bonus 신규 추가

        CCIP가 예측한 낙하점(d_impact)과 실제 착탄 오차(d_error)의
        차이가 작을수록 추가 보상을 준다.
        20 * exp(-0.1 * |d_impact - d_error|)

        → CCIP 예측이 신뢰할 수 있는 상황에서 drop하도록 유도한다.

    거리별 총 보상 비교 (예측 오차 0 가정):

      ┌───────────────┬────────┬────────┐
      │ d_error        │  이전   │  현재   │
      ├───────────────┼────────┼────────┤
      │ 0m  (jackpot)  │  350   │  200   │
      │ 1m             │  224   │  111   │
      │ 5m             │  172   │   38   │
      │ 10m            │  155   │   31   │
      │ 15m            │  151   │   30   │
      │ 50m (즉시drop) │  150   │    6   │
      └───────────────┴────────┴────────┘

      이전: 최고(0m)와 최저(50m)의 차이가 2.3배 → 둔감
      현재: 최고(0m)와 최저(50m)의 차이가 33배  → 민감

  ─── Layer 1: 안전 페널티 (스케일 축소) ────────────────────────────

    ┌──────────────────────┬────────┬────────┐
    │ 항목                  │  이전   │  현재   │
    ├──────────────────────┼────────┼────────┤
    │ crash (저고도 추락)    │  -100  │  -50   │
    │ overspeed (과속)      │   -50  │  -30   │
    │ bad_attitude (뒤집힘) │   -50  │  -30   │
    │ timeout (시간 초과)    │   -30  │  -15   │
    └──────────────────────┴────────┴────────┘

    페널티가 너무 크면 터미널 보상의 분산이 커져서
    critic이 매 step의 접근 신호("타겟 쪽으로 가면 좋다")를 학습하지 못한다.
    전체 터미널 보상 범위를 ±400에서 -50~+200으로 줄여
    접근 보상과의 비율을 맞췄다.

    timeout 페널티는 -30에서 -15로 더 줄였는데,
    이 값이 크면 "끝까지 시도하기"보다 "빨리 crash해서 끝내기"가
    더 나은 전략이 되어 버리기 때문이다.

  ─── Layer 2: 안정성 (변경 없음) ───────────────────────────────────

    매 step:
      - 시간 지연 페널티        -0.05
      - 기체 불안정(각속도²)     -0.05
      - 급격한 조작(Δaction²)   -0.05

  ─── Layer 3: 타겟 접근 (변경 없음) ────────────────────────────────

    매 step:
      R3 = 0.5 * (이전 거리 - 현재 거리)        거리 감소분 보상
         + 0.7 * cos(heading) * speed_gate      진행 방향 정렬도
         + 0.4 * exp(-0.05 * d_impact) * gate   CCIP 정확도

    speed_gate = min(수평속도 / 2, 1)
      정지 상태에서 heading/impact 보상을 받지 못하게 막아
      제자리에 머무르며 보상을 축적하는 편법을 차단한다.

    이 layer 자체는 올바르게 동작하고 있었다.
    문제는 Layer 4의 스케일이 너무 커서 이 신호가 묻혔던 것이다.


================================================================================
 4. 투하 메커니즘 — 자동 전용에서 하이브리드로
================================================================================

  [ 이전: 자동 투하만 존재 ]

    d_impact(CCIP 예측 낙하점) ≤ 10m이면 즉시 자동 투하.

    문제:
      에이전트가 투하 시점을 결정할 수 없다.
      예측 낙하점이 10m 안에 처음 들어오는 순간 강제로 drop이 발동되므로,
      "더 가까이 가서 정밀하게 투하하겠다"는 전략 자체가 불가능하다.
      action[4](투하 행동)가 학습에 전혀 기여하지 못했다.

  [ 현재: 하이브리드 투하 ]

    수동 투하 = action[4] > 0.5  AND  step ≥ 10
    자동 투하 = d_impact ≤ 2.0m  (안전망)

    둘 중 하나가 충족되면 투하 발동 (1회에 한해).

    설계 의도:
      - 에이전트가 action[4]를 통해 직접 투하 시점을 결정하도록 한다.
      - step ≥ 10 조건으로 이륙 직후 무의미한 투하를 방지한다 (약 0.5초 유예).
      - 자동 투하(2m)는 "거의 확실한 상황"에서만 작동하는 최소한의 안전망이다.
      - 앞서 설명한 proximity bonus와 결합되어,
        멀리서 즉시 투하하면 보상이 거의 없고 가까이 가서 투하해야 보상을 받는다.

    추적:
      WandB에서 수동/자동 투하 횟수를 분리 기록한다.
      학습이 진행되면서 수동 비율이 올라가면,
      에이전트가 스스로 투하 시점을 학습하고 있다는 증거가 된다.

 5. 에피소드 종료 조건 정비
================================================================================

  [ 이전 ]

    ┌──────────────────┬──────────────────────────────┐
    │ 조건              │ 기준                          │
    ├──────────────────┼──────────────────────────────┤
    │ crash (저고도)     │ 고도 < 3m, step > 10 이후     │
    │ overspeed         │ 속도 > 20 m/s                │
    │ ang_vel           │ 각속도 > 2.0 rad/s            │
    │ inverted          │ roll 또는 pitch > 60도        │
    │ timeout           │ 500 step 도달                 │
    └──────────────────┴──────────────────────────────┘

    문제:
      지면에 닿아 바운스해도 종료되지 않아 무의미한 에피소드가 이어졌고,
      타겟 반대 방향으로 날아가도 500 step까지 기다려야 해서
      학습 시간이 크게 낭비됐다.

  [ 현재 — 3가지 추가 ]

    ┌──────────────────┬──────────────────────────────┬─────────┐
    │ 조건              │ 기준                          │ 페널티   │
    ├──────────────────┼──────────────────────────────┼─────────┤
    │ ground contact   │ 고도 < 0.5m (step 무관)       │ -50     │
    │ crash (저고도)    │ 고도 < 3m, step > 1 이후      │ -50     │
    │ overspeed        │ 속도 > 20 m/s                 │ -30     │
    │ ang_vel          │ 각속도 > 2.0 rad/s            │ -30     │
    │ inverted         │ roll 또는 pitch > 60도         │ -30     │
    │ out_of_range     │ 타겟까지 거리 > 100m           │ -30     │
    │ timeout          │ 500 step (투하 미발동 시)       │ -15     │
    └──────────────────┴──────────────────────────────┴─────────┘

    ground contact  고도 0.5m 미만이면 step과 무관하게 즉시 crash 처리.
                    → 지면 바운스 에피소드 제거.
    out_of_range    타겟에서 100m 이상 벗어나면 에피소드 조기 종료.
                    → 역주행 에피소드를 빨리 끊어 학습 효율 향상.
    crash 유예      step 10 → step 1로 앞당겨 거의 즉시 적용.


================================================================================
 6. 학습 설정
================================================================================

  ─── SAC 하이퍼파라미터 ────────────────────────────────────────────

    ┌─────────────────┬─────────┬──────────────────────────────────┐
    │ 파라미터         │   값     │ 비고                              │
    ├─────────────────┼─────────┼──────────────────────────────────┤
    │ learning_rate   │ 3e-4    │ SAC 표준값                        │
    │ buffer_size     │ 500,000 │ 초기 100K에서 확대 (경험 보존)      │
    │ batch_size      │ 256     │ 표준값                            │
    │ tau             │ 0.005   │ target network soft update 표준   │
    │ gamma           │ 0.995   │ 유효 horizon ≈ 200 step          │
    │ gradient_steps  │ 1       │ 4에서 critic 발산 → 1로 복구       │
    │ net_arch        │ [256,256]│ 2-layer MLP                     │
    │ device          │ cuda    │ GPU 가속                          │
    └─────────────────┴─────────┴──────────────────────────────────┘

    주요 결정 두 가지:

    gradient_steps = 1
      4로 설정했을 때 critic loss가 17,000까지 치솟았다.
      큰 터미널 보상과 작은 step 보상이 섞인 데이터를 4배 빈도로
      학습하면서 Q값 추정이 불안정해진 것이 원인이다.
      1로 되돌린 뒤 critic이 안정적으로 유지되는 것을 확인했다.

    gamma = 0.995
      유효 horizon이 약 200 step이 되어,
      드론이 당장 다음 step이 아닌 수십 초 후의 투하 성공을 고려해
      비행 경로를 계획할 수 있게 된다.

  ─── 환경 파라미터 ─────────────────────────────────────────────────

    ┌────────────────────┬────────┬──────────────────────────────────┐
    │ 파라미터            │   값    │ 비고                              │
    ├────────────────────┼────────┼──────────────────────────────────┤
    │ action_vx_scale    │ 8 m/s  │ 15에서 축소 (초기 튀어나감 방지)    │
    │ action_vy_scale    │ 5 m/s  │ 유지                              │
    │ action_vz_scale    │ 3 m/s  │ 유지                              │
    │ action_yaw_scale   │ 1 rad/s │ 유지                             │
    │ action_rate_limit  │ 0.2    │ step당 행동 변화량 제한 (급조작 방지) │
    │ max_steps          │ 500    │ 약 25초 (20Hz 기준)               │
    │ min_altitude       │ 3.0m   │ 안전 최저 고도                     │
    └────────────────────┴────────┴──────────────────────────────────┘

  ─── 모니터링 설계 (WandB) ─────────────────────────────────────────

    학습 추적을 위해 WandB callback을 직접 구현했다.

    핵심 metric:
      total_drop_manual_count  에이전트가 직접 투하한 횟수 (누적)
      total_drop_auto_count    안전망(2m)이 발동한 횟수 (누적)
      total_success_count      착탄 오차 ≤ 5m 달성 횟수 (누적)
      total_jackpot_count      착탄 오차 ≤ 0.1m 달성 횟수 (누적)
      drop_error_actual_m      실제 착탄 오차 (m)
      mean_d_xy                타겟까지 평균 거리
      total_truncate_*_count   종료 사유별 누적 (crash/overspeed/inverted/out_of_range 등)

    설계상 결정:
      비율(rate) 대신 누적 횟수(count)를 사용한다.
      짧은 rollout에서 비율이 0과 1 사이를 진동하여 추세를 읽기 어려웠기 때문이다.
      누적 횟수는 단조 증가하므로 추세가 명확하다.

      x축도 총 step 수 대신 총 에피소드 수를 기준으로 잡았다.
      에피소드 길이가 54~500 step으로 들쭉날쭉하여
      step 기준으로는 학습 진척도를 비교하기 어렵기 때문이다.
