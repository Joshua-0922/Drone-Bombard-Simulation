********************************************************************************
*  PART 4 — Hover Exploit 분석 (Issue #017)
********************************************************************************

  발견:
    drop_error 13~16m 구간에 16건 (15.4%)
    특히 14.87m = sqrt(11² + 10²) = 스폰→타겟 거리 정확 매칭
    n_steps 600+ → 스폰에서 random_drop 발동까지 대기

  원인:
    - w_heading 0.7 × 600 step hover = +420 (큰 수익)
    - random_drop 자동 발동 → episode 안전하게 종료
    - 안전한 +422 vs 위험한 success +50~-50
    → agent에게 hover가 합리적 선택

  검토한 7가지 해결책:
    A. w_heading 감소 (heading 보상 약화)
    B. Speed-gated heading 엄격화
    C. 거리 기반 per-step 페널티 (멀리 있으면 비용)
    D. Hover 명시적 감지
    E. Random drop 위치 페널티
    F. Time penalty 강화
    G. Stagnation truncate (기각)

  결정: A + C 조합 (가장 자연스럽고 부작용 적음)

    초반: 정상 학습 (0~50k success 1건, drops 7+11+7+5+4=34건)
    후반: 발산
      - 56~70k: 큰 양수(+274, +187) + 큰 음수(-184, -256) 교차
      - ent_coef 0.58 → 1.5 → 6.03 폭주 (정상 0.3~0.5)
      - critic_loss 100 → 1000 → 230,000+ (정상 100~500)
      - ep_len 310 → 143 감소
      - ep_rew -13 → -33 악화

  발산 원인 정밀 분석:
    1. Round 4 처방의 핵심:
       w_heading: 0.7 → 0.3 (per-step heading 보상 축소)
       w_distance_penalty: 0.03 신규 (per-step 페널티)
       → Per-step 보상 magnitude 축소

    2. 보상 비율 변화:
       Round 3: per-step ~0.7 vs drop ~200 → 1:300
       Round 4: per-step ~0.3 vs drop ~200 → 1:700 (2배 sparse)

    3. SAC auto-entropy 발산 모드 트리거:
       a) Reward sparsity ↑ → critic estimate variance ↑
       b) Policy가 dominant 신호 (drop)에 집중 → entropy ↓
       c) SAC: "exploration 부족" 판단 → ent_coef ↑
       d) Bounded action space [-1, 1] → entropy 못 올라감
       e) SAC: "여전히 부족" → ent_coef ↑↑
       f) 양성 피드백 → 6.03 발산

    교훈: Per-step 보상 magnitude 변경은 SAC 발산 위험.
          Hover 차단은 다른 방법 필요 (terminal signal 등).


********************************************************************************
*  PART 7 — Round 5 결정 (Hover Terminal Penalty)
********************************************************************************

  사용자 제안: episode 종료 시 hover 판단 후 1회 페널티
  장점:
    - Per-step 보상 density 그대로 → SAC 안정성 유지
    - Terminal 신호 추가만 → 발산 모드 회피
    - "잠시 hover OK, 지속 hover BAD" 자연스러운 표현

  Hover 감지 방법 5가지 검토:
    A. 속도 기준 연속 정체 ★ (선택)
    B. 거리 진전 없음
    C. 최소 거리 갱신 간격
    D. 총 정체 시간 누적
    E. 위치 분산

  방법 A 채택 이유:
    - Round 3 hover 패턴: 14.87m 클러스터 = "스폰에서 거의 안 움직임"
    - 속도 < 1 m/s가 정확히 그 상태
    - 단순, 직관적, 부작용 적음

  파라미터:
    hover_speed_threshold = 1.0 m/s     (정지 판단)
    hover_consecutive_threshold = 200 step (지속 임계, episode 25%)
    penalty_hover = -15                  (timeout과 동일)
    Drop 시 (terminated) 제외 — 정밀 hover 정당

  Round 4 처방 복원:
    w_heading: 0.3 → 0.7 (Round 3 수준)
    w_distance_penalty: 0.03 → 0 (비활성)

  코드 변경:
    drone_drop_env.py:
      reset(): _consecutive_still = 0, _max_consecutive_still = 0 추가
      step(): speed_xy < threshold이면 consecutive ↑, 아니면 0
              max 갱신
              episode 종료 시 (truncated AND not dropped):
                if max_consecutive_still > 200: reward -= 15
    hyperparams.yaml:
      hover_speed_threshold, hover_consecutive_threshold, penalty_hover 추가
      run_name → round5_hover_terminal_penalty

  Round 5 학습 시작 (run sdjytkpv, 300k)
