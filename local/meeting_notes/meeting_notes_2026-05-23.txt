이번 세션은 사용자 통찰이 진단 + 처방의 거의 모든 부분을 주도. 정리 :

─── 2-1. 진단 측 통찰 ─────────────────────────────────────────────────────────

① "훈련이 전혀 안 되고 있어"
   → SAC 안정성과 정책 학습은 별개 — junsang_v3 의 critic 18.5 안정 vs
      mean_d_xy 19.46m 정체. M2 단독 lever 만으론 부족.

② "드론이 바닥에 부딪혀 튕기는 장면이 많아"
   → P4 (고도 최저선) + P5 (crash penalty) + P11 (inverted) 진단 트리거

③ "시작하자마자 막 튀어나가거나"
   → P1 (action_vx_scale 15) + P2 (가속도 제한 없음) 진단

④ "중간부터 이상하게 학습되는 경우 많음"
   → P9 (early termination 부재) → bad transition buffer 누적 진단

⑤ "안 좋은 학습은 시작부터 과감히 쳐내야"
   → P9 + P11 처방의 핵심 — 망가진 sample 즉시 episode 종료

⑥ "drops 발생해도 학습 안 됨"
   → P6 (CCIP threshold 4m 빡셈) — drops 가 우연 효과지 학습된 행동 아님

─── 2-2. 처방 측 통찰 ─────────────────────────────────────────────────────────

① "훈련의 목표를 2m 아니라 10m 안으로 → 일단 성공"
   → P6 처방 : auto_drop_threshold 4 → 10 (curriculum phase 1)

② "바닥 닿으면 안 되는 법칙 추가"
   → P5 처방 : penalty_crash -10 → -100 + crash 시 truncated=True

③ "제한 조건을 강하게"
   → P3 처방 : penalty_overspeed -8 → -50 + truncate

④ "속도 변화 (가속도) 제한"
   → P2 처방 : action_rate_limit 0.2 hard clip (코드 NEW)

⑤ "최대 속도에도 제한"
   → P1 처방 : action_vx_scale 15 → 8

⑥ "고도에도 최저선"
   → P4 처방 : min_altitude 2 → 3, start_step 20 → 10

─── 2-3. 메타 통찰 (RL 설계 원칙) ─────────────────────────────────────────────

① "큰 - 를 어떻게 줄건지? 역효과 내진 않을까? 어떻게 설계?"

#  PART 5.  핵심 교훈 (이번 세션의 학습)

─── 5-1. 진단 분리 — SAC 안정성 vs 정책 학습 ──────────────────────────────────

junsang_v2 → junsang_v3 비교가 명확히 보여줌 :
  - junsang_v2 : critic_loss 17K (발산), drops 106 → SAC 측 망가짐
  - junsang_v3 : critic_loss 18 (안정), drops 57 → SAC 측 정상, 정책만 못 배움

→ **SAC parameter (M1/M2/H3) 와 정책 학습 능력은 별개**. SAC 안정성 회복했다고
   학습 성공 보장 X. Env/reward 측 학습 신호가 별도로 필요.


─── 5-2. Hardcoded 값의 함정 ───────────────────────────────────────────────────

drop_attempt_bonus=150, truncation_penalty=-80 두 핵심 reward 가 코드에
hardcoded 였음 (L653, L695). yaml 변경이 사실상 무력했음.

→ **새 prescription 적용 시 grep 으로 실제 사용 위치 확인 필수**.
   yaml 키 추가만으로는 안 됨 — 코드의 self._cfg_* 로드 + 사용처 확인.


─── 5-3. 사용자 GUI 관찰의 가치 ────────────────────────────────────────────────

200k 학습 후 evaluate 의 deterministic policy 를 GUI 로 직접 보지 않았으면
  - wandb metric (mean_d_xy=32m, drops=106) 만으로는 "잘 안 됐다" 정도만
  - GUI 관찰 ("바닥에 부딪혀 튕기다 어디론가") 이 P4/P5/P11 진단의 트리거

→ **학습 끝날 때마다 deterministic evaluate + GUI 관찰 권장**. 수치만으로는
   bad sample 의 정성적 특성 못 봄.


─── 5-4. Reward 설계의 cliff vs gradient ───────────────────────────────────────

junsang N1=B v2 (w_impact=8) 의 per-step 강화 → orbit-milking
jekyun v3 (w_impact=0.4 + drop_attempt_bonus=150) 의 sparse-dense 균형 → critic 폭주
junsang_v3 (M2=1) → SAC 안정 but 학습 동기 부족

해결 = **early terminate + 큰 penalty + reasonable per-step + 큰 terminal bonus**

→ **Reward 설계는 hyperparameter tweak 이 아닌 system design**. parameter
   하나 바꿔서 해결되는 게 아니라 환경/safety/curriculum 의 종합 설계.


─── 5-5. 검토 라운드의 효용 ───────────────────────────────────────────────────

9 회차 검토 결과 48 issue 발견 + 보완.
  - 1차 (3 회) : 13 issue — 표면적 (번호, 일관성)
  - 2차 (3 회) : 21 issue — 누락 (callback, 정량 기준, edge case)
  - 3차 (3 회) : 14 issue — 실제 코드 grep 으로 signature 검증

→ **첫 문서 작성 후 한 번 검토만으로는 부족**. 3 차 (라운드 7-9) 에서 발견된
