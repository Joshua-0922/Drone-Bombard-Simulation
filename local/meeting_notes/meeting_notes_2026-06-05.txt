********************************************************************************
*  PART 9 — 평가 도구 확장: rolling success_rate + current_success_streak
********************************************************************************

  사용자 통찰:
    학습 전체 누적 metric < 시점별 (point-in-time) 성능 측정
    → 학습이 잘 되고 있는지 현재 시점 평가에 더 유용

  Rolling success_rate:
    이미 SB3 에 존재: `rollout/success_rate`
    Definition: ep_info_buffer (default 100 episodes) 의 is_success 평균
    학습 중간 시점 성능 측정 = 마지막 100 episodes 의 성공 비율
    WandB 의 `rollout/success_rate` 로 자동 기록

  Current_success_streak 추가:
    학습 도구만 (reward 영향 X):
      success 시 +1
      실패 (drop with non-success, 또는 drop 없는 episode 끝) 시 0
    동작:
      time: e1  e2  e3  e4  e5  e6  e7  e8
      result: S   S   S   F   S   S   F   S
      streak: 1   2   3   0   1   2   0   1

    WandB metric: env/current_success_streak (시계열 chart)

  연속 성공 가산점 (reward) 검토 — 기각:
    SAC 의 Markov 가정 위반 가능성:
      Replay buffer 의 random sampling 시 streak 맥락 없음
      Variance 증가
      Safe-play 편향 (best drop 정밀도 저하 risk)
      Credit assignment 망가짐
    → reward 로는 적용 X. Metric only 로 한정.

  구현 (callback only, env 무수정):
    train_sac.py:WandbMetricsCallback 에:
      __init__: self._current_success_streak = 0
      _on_step done block:
        drop & is_success: streak += 1
        drop & not is_success: streak = 0
        no drop: streak = 0
      _on_rollout_end: log_dict['env/current_success_streak'] = ...

  적용 범위:
    현재 v2 (이미 실행 중): ❌ (옛 코드 메모리에 로드됨)
    다음 학습부터: ✓ 자동 적용


********************************************************************************
*  PART 10 — Phase 1 redux v2 의 검증 목표
********************************************************************************

  목표 metrics:
    1. 새 1m success_rate > 50%
       (이전 96% at 5m 정책의 정밀화 가능성 입증)
    2. 첫 jackpot 발화 (drop_error < 0.3m)
       (학습 전체 모든 라운드에서 처음)
    3. best drop < 0.3m (jackpot 영역)
       (현재 0.809m → 0.3m 미만으로 정밀화)
    4. fps 5-10 회복
       (kill_infra timeout 효과 측정)

  Decision tree:
    1m success > 50% 도달 → curriculum learning 성공 → 더 좁은 임계 시도 가능
    1m success < 20% → 정책 한계 도달 → reward 구조 재검토 (Phase 3)
    Jackpot 발화 → 정책 정밀도 새 단계 → Phase 2 jackpot 활용 가능
    Fps 5+ 회복 → kill_infra timeout 처방 검증
    Fps 여전히 < 3 → 다른 원인 (e.g. obs_wait_timeout, gz_ms degradation)
