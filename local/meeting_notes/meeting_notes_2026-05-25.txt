################################################################################
#  PART 2.  브레인스토밍 — 문제점 진단
################################################################################

2-1. Drop 보상이 거리에 둔감 (#001)
  15m drop과 5m drop의 보상 차이가 21밖에 안 됨.
  drop_attempt_bonus=150이 지배적 → "대충 drop만 하면 OK" 전략.

2-2. 에피소드 종료 조건 부족 (#002)
  지면 바운스 미차단, out_of_range 미구현.
  드론이 타겟 반대로 날아가도 500 step까지 기다려야 함.

2-3. 보상 스케일 과대 / critic 불안정 (#003)
  터미널 보상 분산(±400)이 per-step 접근 신호(+375)를 덮음.
  critic이 "타겟 접근 = 좋다"를 학습하지 못하는 근본 원인.
  → 드론이 이상한 방향으로 날아가는 이유.

2-4. Deterministic eval drop 0회 (#004)
  stochastic noise로 우연히 drop zone 진입. mean action은 못 감.
  배포 시 문제.

2-5. Replay buffer 오염 (#005)
  500k buffer에 초기 쓰레기 데이터 잔존. 150k 학습에서는 영향 제한적.

2-6. Auto_drop 구조적 한계 (#006)
  d_impact이 처음 threshold 이하가 되는 순간 강제 drop.
  에이전트가 "더 기다려서 정밀하게" 할 수 없음.
  → hybrid drop (manual + auto 안전망) 제안.

2-7. CCIP 예측 갭 (#007)
  CCIP 예측(d_impact) vs 실제(drop_error) 사이에 체계적 오차.

2-8. Observation/Action 충분성 (#008)
  분석 완료: obs/action은 구조적으로 충분.
  병목은 학습 체계(보상 + drop 메커니즘).

2-9. Phase 1 졸업 기준 불명확 (#009)
  현재 기준(drops≥30 등)이 신뢰 불가. 결과 보고 재정립 필요.

2-10. 분리/착탄 이중 보상 (#010)
  release 조건 + actual error + CCIP 일치도 3요소 보상.
  Round 2 후보로 보류.

#  PART 8. Issue #015 — 좌표 오프셋 의심 → replay 한계 발견
################################################################################

  GUI에서 drop episode replay 시 드론이 타겟을 30m 지나쳐서 drop.
  학습 데이터에서는 d_xy=4.6m.

  디버깅 결과:
    - obs vs Gazebo 좌표: 첫 에피소드에서 일치 (오프셋 0.2m)
    - replay가 30m 차이나는 이유: open loop (저장된 action 재생, obs 안 봄)
      → 초기 0.01m 차이가 420 step 뒤 30m로 발산
    - deterministic evaluate (closed loop)로 검증: obs ≈ Gazebo 일치 확인
    - 좌표 문제 없음. replay 방식의 근본적 한계.

  결정:
    - action replay 폐기 → deterministic evaluate + GUI가 올바른 검증 방법
    - best drop 시 모델 가중치(.zip) 저장 추가 (action 저장은 재현 불가)
