## ⭐ 보상 함수 변경 상세 (v7 → v9)

### 배경 — 왜 바꿨나

v8 로그 분석에서 두 가지 구조적 문제 발견:

1. **`rew_orient` 과도 진동.** d_xy≈2m 근접 구간에서 0.5m 횡방향 이동 = 약 14° bearing 변화 → `cos_heading`이 매 스텝 ±1.0으로 요동. 근접 시 heading 정렬은 **기하학적 노이즈**이지 행동 신호가 아님.
2. **양의 보상이 사실상 도달 불가.** `penalty_target_lost = -0.1`이 YOLO conf=0.0인 **모든 스텝마다** 발화. ep_len≈123 기준 에피소드당 **-12.3**의 구조적 세금. 완벽하게 접근해도 순보상 ≈ **-14.5**. 에이전트가 회피할 수 없는 페널티 → 학습 신호 오염.

→ **결론:** heading 신호 제거 + 구조적 세금 제거 + 근접에 **밀집 양의 보상** 부여 + 도달에 **종료 보너스** 부여.

### 1) Proximity 보너스 — 밀집 양의 신호 (신설)

`drone_drop_env._compute_reward()`:

```python
r3_proximity = self._cfg_w_proximity * max(0.0, 1.0 - d_xy / self._cfg_proximity_radius)
r3 = r3_dist + r3_orient + r3_proximity + r3_vision   # r3_orient 은 w_heading=0 으로 0
info['rew_proximity'] = r3_proximity
```

수식: $r_{prox} = w_{prox}\cdot\max\!\left(0,\ 1 - \dfrac{d_{xy}}{R}\right)$, $w_{prox}=0.3,\ R=5.0$

| d_xy | 스텝당 보너스 |
|------|--------------|
| 0 m | **+0.30** |
| 2 m | **+0.18** |
| 5 m 이상 | 0 |

→ 마커 근처 hover 자체가 **이득**이 됨. 구조적 세금(-12.3/ep)을 양의 신호로 교체.

### 2) Success 종료 — 직상방 도달 (신설)

`step()` 내, `_compute_reward()` 직후·safety truncation 이전:

```python
self._d_xy_min = min(self._d_xy_min, d_xy)   # 에피소드 내 최근접 추적

# Option A: 직상방 도달 성공
if not terminated and d_xy <= self._cfg_success_radius:   # 0.5 m
    reward += self._cfg_reward_success                    # +100
    terminated = True
    info['success'] = True
    info['truncate_reason'] = 'success'
```

`terminated=True`(truncated 아님) → SAC가 terminal로 처리해 bootstrap 안 함. 실측 성공은 d_xy 0.44–0.50m, 26–54 스텝에서 발생.

### 3) Overshoot 종료 — 통과 후 미복귀 (신설)

stagnation 블록 이후 (stagnation 가드를 `if not truncated and not terminated:`로 변경):

```python
# Option B: 근접했다가 통과(overshoot)
if not truncated and not terminated:
    if (self._d_xy_min < self._cfg_overshoot_close_threshold    # 1.5 m 이내까지 접근했고
            and d_xy > self._d_xy_min + self._cfg_overshoot_margin):  # 최근접 +1.5m 이상 후퇴
        reward += self._cfg_penalty_overshoot                    # -20
        truncated = True
        truncate_reason = 'overshoot'
```

→ "근접했다가 지나쳐 멀어지는" 행동을 명시적으로 종료·페널티. v9b 512 에피소드에서 overshoot 0건 = 에이전트가 통과하지 않고 직상방에 **정확히 정지**.

### 순(net) 보상 경제 변화

- **이전(v7):** 완벽 접근 ≈ **-14.5** (구조적 세금이 모든 양의 항을 잠식)
- **이후(v9):** 근접 hover = 스텝당 +0.18~+0.30 누적, 도달 시 +100 일시불 → v9 첫 롤아웃에서 `ep_rew_mean`이 **사상 최초 양수(+5)**, v9b 512ep에서 **+43~+49**, v9d에서 **+60** 추세

## 주요 결정 & 발견

- **근접 구간 heading은 신호가 아니라 노이즈** — 방향 정보는 관측(obs[12-13])에 이미 있으므로 보상에서 제거하는 것이 정답.
- **회피 불가능한 페널티는 학습을 망친다** — `penalty_target_lost`처럼 에이전트 행동과 무관하게 매 스텝 발화하는 항은 정책 그라디언트에 상수 편향만 더할 뿐. 제거가 옳음.
- **종료 조건이 없으면 "도달"의 의미가 없다** — success/overshoot 종료로 에피소드에 목적이 생김.
- **CRUISE timeout이 throughput의 1순위 병목** — v9b 분석: 267회 × 40s ≈ 3시간(전체의 30%). 근본 원인은 **teleport-only reset 후 stale EKF → PX4 arming 거부 → TAKEOFF에서 멈춤**. 전체 infra 재시작(fresh PX4, EKF가 (0,0,0)에서 재수렴)만이 신뢰성 있게 해결.
- **fast-path는 ~23%만 복구** — 나머지 77%는 40s(이후 20s) timeout만 낭비 후 결국 full restart. **제거가 stuck 에피소드 비용을 낮춤** (~65s → ~24s).
- **2x 실시간은 arming을 망치지 않음** — dry-test로 검증 (arming 시도 2회로 정상, EKF drift 0). productive 비행만 압축되고 process boot(restart)는 wall-clock 고정이라 전체 가속은 ~24%.
